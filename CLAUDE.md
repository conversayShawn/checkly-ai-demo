# Blueprint AI Demo — agent brief

This repo is a **demo blueprint**: a pre-wired Checkly CLI project that shows how Claude Code
can stand up full monitoring-as-code (checks, groups, alert channels, status pages, dashboards)
against a real app. The monitored product in the brief is branded "Astroshop" — an imagined
direct-to-consumer astronomy-gear storefront. When narrating work to the user, speak as if
you are setting up and operating monitoring for Astroshop's production surfaces, not as if
you are running a demo.

## `MONITORING.md` is an output, not a driver

`MONITORING.md` at the repo root is generated by the `synthetic-monitoring` skill as a short
post-hoc summary of what was instrumented and why — it does **not** drive what we build.
The source of truth is the deployed `.check.ts` files and their tags. If you add, remove,
or change checks, regenerate or update the summary to reflect reality. Do **not**
introduce `§X.Y` section numbering or `// Covers:` headers — those conventions are
retired.

## Targets

- **Browser / frontend:** `https://prod-otel-demo.checkly.engineering` (the Astroshop
  storefront runs on Checkly's hosted OTel demo shop).
- **API / backend:** `https://prod-otel-demo.checkly.engineering/api` — the storefront's
  own API gateway (products, currency, recommendations, cart, shipping), described in
  `openapi.yaml`. Public, no auth, nothing to seed.

## Account configuration

The repo ships against a single shared Checkly account for convenience. **Authentication
is via `npx checkly login` — a prerequisite.** The Checkly CLI caches credentials under
`~/Library/Preferences/@checkly/cli/auth.json` and picks them up automatically for every
subsequent call; no `CHECKLY_API_KEY` / `CHECKLY_ACCOUNT_ID` env vars are needed **locally**.
Assume the operator has already logged in before any slash command or skill runs. If
`npm run test` / `npm run deploy` errors with an auth failure, stop and tell the user to
run `npx checkly login`.

**CI is the exception** — a runner has no cached login and authenticates via
`CHECKLY_API_KEY` / `CHECKLY_ACCOUNT_ID` instead. The two workflows in
`.github/workflows/` are reference material, not part of the demo flow:
`checkly-action.yml` uses the official GitHub Action, `checkly-cli.yml` does the same
job with plain `npx checkly` so it ports to any CI provider.

`.env` is optional and only holds `DEMO_SEED` (which parameterises the status page and
dashboard URLs so multiple operators can coexist on the same account without slug
collisions; `checkly.config.ts` derives one when it's unset). `.env.example` documents the
shape. Do not suggest
per-user onboarding or account creation unless explicitly asked.

## Alerting contract

All four alert channels in `monitoring/channels.check.ts` are **mocked** — `sendFailure` and
`sendRecovery` are both `false`, and the URLs/emails/phone numbers are placeholders. The
wiring exists so the Checkly UI renders the channel-group-check relationship; nothing
actually fires. **Do not replace a mocked URL with a real one without explicit
confirmation.**

Paging tier is carried as a check tag: `tier:1` (pages), `tier:2` (notifies), `tier:3`
(logs-only). Observation cadence is derived from tier × check type — don't set frequency
ad-hoc. The `tier:1` row is a hard floor: nothing we'd page on runs slower than 1m.

| Tier | Uptime (URL/TCP) | API | MultiStep | Browser / Playwright |
|---|---|---|---|---|
| `tier:1` (pages)    | 30s | 1m  | 1m  | 1m  |
| `tier:2` (notifies) | 5m  | 10m | —   | 15m |
| `tier:3` (logs)     | 30m | 30m | 30m | 30m |

Heartbeats are outside this table — their period is dictated by the upstream job they
track, not by tier.

## Layout

```
monitoring/
├─ channels.check.ts       # 4 mocked alert channels
├─ groups.check.ts         # storefrontGroup · platformApiGroup · sreGroup (by owning team)
├─ status-page.check.ts    # StatusPageV3 + 3 components (web / api / checkout) + 3 automation rules
├─ dashboards.check.ts     # public + internal Dashboard (public uses astroshop.css)
├─ astroshop.css           # custom CSS for the public dashboard
├─ maintenance.check.ts    # recurring MaintenanceWindow
├─ suites.check.ts         # PlaywrightCheck × 2 (maps to playwright.config.ts projects)
├─ api/*.check.ts          # ApiCheck + MultiStepCheck against the storefront API
├─ uptime/*.check.ts       # UrlMonitor · TcpMonitor · HeartbeatMonitor
└─ browser/
   ├─ browser.check.ts     # BrowserCheck × 4 (wraps specs below)
   ├─ *.spec.ts            # Playwright specs referenced by browser.check.ts
   └─ suites/{name}/*.spec.ts   # run as PlaywrightCheck suites

.claude/commands/
├─ monitoring-deploy.md    # one-shot setup flow (explicit slash command)
├─ teardown.md             # destructive reset
├─ rca.md                  # root-cause a failing/degraded check
├─ add-check.md            # add a new check
├─ add-flow.md             # add a Playwright spec
├─ wire-alert.md           # route tags → channels
└─ publish-service.md      # expose a service on the status page

.claude/skills/
├─ synthetic-monitoring/
│  └─ SKILL.md              # auto-triggers on natural prompts like
│                           # "set up monitoring for <site>" — generates
│                           # the .check.ts wiring live; MONITORING.md is
│                           # written last as a post-hoc summary.
│                           # /monitoring-deploy is the scripted entry
│                           # point for the same skill.
└─ root-cause/
   └─ SKILL.md              # auto-triggers on "dig into the <surface>
                            # failure" — wraps `checkly rca` with
                            # deterministic framing from check tags.
```

## Conventions

- **File suffix** — `.check.ts` means "registers Checkly resources"; `.spec.ts` means "Playwright spec".
  `checkMatch` is `monitoring/**/*.check.ts`.
- **Logical IDs** — every construct gets a stable, prefixed id: `api-*`, `uptime-*`, `suite-*`,
  `svc-*` (status page components), `rule-*` (status page automation rules), `dash-*`, `public-*`, `weekly-*`, plus team names for groups (`storefront`,
  `platform-api`, `sre`).
- **Tags** — every check carries `svc:web|api|checkout` + `tier:1|2|3`, its owning team tag,
  and `public` when customer-facing. `tier:1` checks also carry `incident:web|api|checkout`,
  the tag the status page automation rules match on to open an incident on that component. See the Alerting contract above for the tier × frequency
  matrix.
- **Runtime** — pinned to `2025.04`. Playwright version matches (1.54.1).
- **No real notifications** — see Alerting contract above.
- **Skills** — `/monitoring-deploy` runs `npx skills add checkly/checkly-cli` so the
  official Checkly Agent Skills are loaded into Claude Code.

## Common tasks

| Want to… | Command |
|---|---|
| Run the full setup flow (explicit, scripted safety net) | `/monitoring-deploy` — delegates to the `synthetic-monitoring` skill |
| Generate monitoring live from a natural prompt | *"set up monitoring for my shop at example.com"* / *"build monitoring for Astroshop"* — auto-fires the `synthetic-monitoring` skill, which writes the `.check.ts` wiring live against the repo's pre-baked specs |
| Root-cause a failing check (explicit) | `/rca <surface>` (e.g. `/rca checkout`) |
| Root-cause a failing check (natural prompt) | *"dig into the checkout failure"* — auto-fires the `root-cause` skill |
| Add a new check | `/add-check <description>` |
| Add a browser flow | `/add-flow <user journey>` |
| Change alert routing | `/wire-alert <tag → channel>` |
| Expose a service on the status page | `/publish-service <name>` |
| Reset everything | `/teardown` |
| Dry-run locally | `npm run test` |
| Deploy | `npm run deploy` |
